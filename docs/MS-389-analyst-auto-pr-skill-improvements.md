# MS-389 — Analyst auto-PRs skill improvements from rubric scores and failure patterns

## What & why

Closes the self-improvement loop started in MS-380. After each worker job is scored by the
Analyst (MS-405), the Analyst now checks whether the same quality problem has appeared 3+ times
in a 7-day window. If so, it reads the relevant `.claude/commands/` skill file from GitHub, asks
Claude to propose a minimal edit, and opens a pull request to a `feedback/analyst-YYYY-MM-DD`
branch for human review.

**Two detector types:**

- **GateFailure** — same `failed_gate` (`compile` / `tests` / `detekt` / `ci`) in 3+ FAILED jobs
- **LowRubricScore** — rubric criterion averaged below 3.5/5 across 3+ jobs

A human reviews the diff and merges (or closes). The Analyst never self-merges.

## Architecture

Three new layers, each independently testable:

```
PatternDetector           — detects recurring issues in Supabase
GitHubApiClient           — reads and writes to GitHub
SkillPrService            — orchestrates the full flow (detect → synthesize → PR)
```

All three are wired via Koin in `AnalystModule` and called from the existing Pub/Sub
fire-and-forget coroutine in `PubSubCompletionRoutes` after `decisionScorer.score()`.

## Pattern detection

`DatabasePatternDetector` runs two raw SQL queries via Exposed `transaction { exec(sql) }`,
the same pattern as `JobsTableStatsReader`. No new query framework was added.

**Gate failure query:**
```sql
SELECT failed_gate, COUNT(*) AS run_count
FROM jobs
WHERE status = 'FAILED'
  AND failed_gate IS NOT NULL
  AND created_at >= now() - make_interval(days => 7)
GROUP BY failed_gate
HAVING COUNT(*) >= 3
ORDER BY run_count DESC
```

**Low score query** (joins `decision_scores` + `jobs`):
```sql
SELECT ds.criterion,
       AVG(ds.score) AS avg_score,
       COUNT(DISTINCT ds.job_id) AS run_count
FROM decision_scores ds
JOIN jobs j ON j.id = ds.job_id
WHERE j.created_at >= now() - make_interval(days => 7)
GROUP BY ds.criterion
HAVING AVG(ds.score) < 3.5 AND COUNT(DISTINCT ds.job_id) >= 3
ORDER BY avg_score ASC
```

## GitHub App authentication — pure JDK, no Bouncy Castle

GitHub App auth requires a JWT signed with RS256, then exchanged for a short-lived installation
token. The standard library approach avoids a new dependency.

**JWT construction:**
1. Build `header.payload` as base64url-encoded JSON
2. Sign with `java.security.Signature` (SHA256withRSA)
3. Append signature as third base64url segment

**Private key loading** supports both PKCS#1 (`BEGIN RSA PRIVATE KEY`) and PKCS#8
(`BEGIN PRIVATE KEY`). PKCS#1 keys need to be wrapped in a PKCS#8 envelope before
`KeyFactory.getInstance("RSA")` can parse them. The wrapper is 20 lines of DER TLV encoding —
no third-party library needed.

```kotlin
// PKCS#8 DER wrapping: RSA OID + version + raw PKCS#1 bytes
private fun wrapPkcs1(pkcs1: ByteArray): ByteArray {
    val algId = byteArrayOf(0x30, 0x0d, 0x06, 0x09, ...)  // RSA OID
    val version = byteArrayOf(0x02, 0x01, 0x00)
    val inner = version + algId + derTlv(0x04, pkcs1)
    return derTlv(0x30, inner)
}
```

## Patch synthesis — one bounded Claude call, not an agent loop

The PR content is generated by a single Claude API call with tool-use forcing. This is NOT a
multi-turn agent loop — that pattern belongs in workers (open-ended reasoning). Here the prompt
is fully bounded: pattern evidence + current skill file → `proposed_content` string.

```kotlin
// Tool schema forces a structured string response
val patchTool = buildJsonObject {
    put("name", "propose_patch")
    putJsonObject("input_schema") {
        put("type", "object")
        putJsonObject("properties") { putJsonObject("proposed_content") { put("type", "string") } }
        putJsonArray("required") { add("proposed_content") }
    }
}
val toolChoice = buildJsonObject { put("type", "tool"); put("name", "propose_patch") }
```

## Optional wiring — graceful degradation

The PR feature is disabled when any of the five `GITHUB_*` env vars is blank. Koin registers
`SkillPrService` only when all five are present; otherwise it logs and skips. The call site uses
`getKoin().getOrNull<SkillPrService>()` for optional injection.

```kotlin
// AnalystModule.kt — only registered when fully configured
if (isGithubConfigured(config)) {
    single<SkillPrService> { SkillPrService(...) }
}

// Application.kt — optional injection
val skillPrService: SkillPrService? = getKoin().getOrNull()
```

## Env vars added to Cloud Run (analyst service)

```
GITHUB_APP_ID          — integer string, e.g. "123456"
GITHUB_PRIVATE_KEY     — PEM-encoded RSA key (PKCS#1 or PKCS#8)
GITHUB_INSTALLATION_ID — e.g. "135953548"
GITHUB_REPO_OWNER      — e.g. "michael-gonzalez-dev"
GITHUB_REPO_NAME       — e.g. "media-sage"
```

## Testing strategy

| File | What it tests |
|---|---|
| `GitHubAppClientJwtTest` | JWT 3-segment structure, RS256 header, `iss` payload, signature verification, PKCS#8 key loading |
| `SkillPrServiceTest` | Skips when no patterns; skips when PR already open; correct branch name; correct skill path written; only first pattern fires; low score pattern also triggers PR |

`DatabasePatternDetector` has no direct unit test — PostgreSQL-specific SQL (`make_interval`)
can't run in H2. Coverage comes from the `FakePatternDetector` in `SkillPrServiceTest`.

## Detekt note

`analystModule` in `AnalystModule.kt` carries `@Suppress("LongMethod")`. Koin DI wiring functions
are inherently verbose — their length is a structural constraint, not a complexity problem. This is
the idiomatic suppression pattern for DI module builders in this codebase.
